# Invariant 8: Unlink is cloud-first

Read before touching `CloudSync+Unpairing`, `zoneGoneVerdict`, `AppModel+Pairing`, `createPairInvite`, account checks, subscription clean-up.

**Unlink is cloud-first.** `unpair()` succeeds before local state is cleared; `forceLocalReset` is the escape hatch. "Zone gone" under a *different* iCloud account never wipes (`SyncError.differentAccount`).
- **"Zone gone" needs a second sighting** (`CloudSync.zoneGoneVerdict`), since the close handshake takes the partner off the share for seconds: the first stamps `SharedStore.zoneGoneSeenAt` and throws the transient `SyncError.zoneUnreachable`; one `zoneGoneConfirmation` later wipes and throws `linkEnded`; a successful fetch clears the stamp.
- That wipe spares own unsent sends (`eraseLocalMedia(keepingPendingUploads: true)`) and remembers the zone (`clearPairing(keepingName: true)` → `SharedStore.lastPairing`); `acceptShare`/`rejoin` (`adoptPairing`) skip the wipe for that zone, so the re-tapped link re-sends them. A different zone, a new invite or "start over" wipes.
- A new invite never reuses a zone with someone on its share or any records: `createPairInvite` refuses with `SyncError.existingPairing` (Rejoin offered; `replacingExisting: true`, confirmed, deletes the zone first). It fails closed — `leftoverZone` throws on an unreadable lookup, `existingZoneShare` on anything but "gone", `reopened` refuses rather than evicts. `SharePosture.memberCount` counts people once, never leavers. `discoverExistingPairing` doesn't offer Rejoin into a share with a blocked person (`ownerShareIsRejoinable`; an unreadable share only when nobody is blocked), and a look that failed (or an account `temporarilyUnavailable`/`couldNotDetermine`) is `PairingDiscovery.unknown`, never "none": the pairing screen tries again a few times; the invite button's own look is one.
- Mid-refresh guards compare by `PairingInfo.sameZone(as:)`, so an unlink-and-re-pair can't file the ex's delta or token on the new pairing (`createPairInvite` clears tokens like `acceptShare`); an unlink mid-refresh stops `apply` past the status write and skips the token persist; a token cleared *during* `apply` isn't written back.
- The owner's zone ID names *whoever is signed in*: `requirePairing`/`unpair` refuse with `differentAccount` on positive proof of a mismatch (`CloudSync.currentUserRecordName`, cached). `refresh` runs that check alongside its fetch, judged before `apply` and the verdict; a cold extension first trusts `SharedStore.verifiedAccount` (same `accountCacheLifetime`, never future-stamped), cleared by `noteAccountChanged`. The app's own lookup lasts `appAccountCacheLifetime` (an hour): it hears `CKAccountChanged`, which drops it; a copy of another process's lookup keeps `accountCacheLifetime` (a cold launch never hears a switch made while it wasn't running), and `zoneGoneVerdict` looks the account up for real before anything is wiped (`isPairingAccount(fresh:)`).
- **Subscriptions outlive an unlink that didn't reach iCloud:** `finishUnlink` (unlink, block, local reset) and the verdict stamp `SharedStore.subscriptionCleanup` with the pairing's account; `AppModel.cleanUpSubscriptionsIfNeeded` retries each foreground while unpaired, bounded, deleting `SubscriptionID.all` from both databases (`unknownItem` = done), refusing on proof of another account, never while paired, re-registering if a pairing appeared mid-delete.
